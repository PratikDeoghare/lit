Brashtag · a notation for trees · a literate programming toolkit

Write the story. The code falls out.

Brashtag is a very small notation for writing trees: you surround text with hints that programs can use later. This page shows one thing built on it, literate programming, and the tools around it. You keep one document that explains the program, while your team goes on editing the code the ordinary way, in any editor. Everything is one program, lit: a single binary with nothing to install around it.

Everything on this page runs in your browser, on the JavaScript build of the brashtag parser. The editors are live: what they print follows the same rules as the lit binary.

What the tools add

Literate programming has a known weak spot: the moment someone edits the generated code, the document is out of date. These pieces are about that moment.

Your own literate fork

Nobody has to agree on a narrative. With an assistant, anyone can turn a codebase into their own literate version, written the way they want to read it, and customise it as they like. The one thing that is shared is the tangled output: the code.

How it works

Gaps for an assistant

Leave #agent-fill-in{what this must do} inside a chunk. lit fill gathers the context from the whole document, asks an assistant for the code, checks it and writes it in. lit review checks it again.

Not everyone has to be literate

Be the literate programmer while your team works on the code in the traditional way: absorb. Their edits to a generated file are folded back into your document, into the right chunk, with the right indentation.

Try it in the lab

Sync

Edit the document and the code on the same day. A three-way merge against the last agreed state brings every separate change across, both ways, and asks you only about real conflicts. Nothing is lost; replaced edits are kept.

Try it in the lab

Sourcemaps

Tangle records where every generated line came from. Ask in either direction: this line of app.py, which line of the document wrote it? This line of the document, where does it end up? Absorb and sync are built on the same map.

A notation that goes further

Brashtag is small enough to learn in a minute and powerful enough to write tools with. Literate programming is one use. The same trees drive flashcards, HTML pages and diagrams.

Any editor

A document is plain text and the tools are one command-line program, so there is no plugin to install and no editor to switch to. Addresses come out as path, line and column, the form editors and grep already read.

Get the understanding back

Agents write code faster than people read it, and old code outlives the people who understood it. Either way you end up owning a program you can run but cannot explain. Claude can read a codebase and write the explanation down, so make the explanation the program. This works on legacy code too: the tutorial below starts from a script with no comments worth the name.

It also means you do not have to adopt anyone else's explanation. A literate version is a fork that costs one prompt: you can have your own, in your own order and your own words, and a colleague can have a different one of the same code. Because tangling is a function of the document, every fork produces the same files, so the tangled output is the only thing that has to be agreed upon. And nobody is obliged to work in the document at all: a teammate who edits the generated code is folded in by absorb.

  1. Install the skill

    The binary carries the skill inside it; one command puts it where Claude looks.

    lit install-skill

  2. Ask Claude to literate it

    Point it at a file, a module or a whole codebase. It reads the code, plans a narrative, and cuts the code into named chunks without changing a line.

  3. Read it, and check it

    Weave gives you a page to read in the order that teaches the code. Tangle writes the code back, and a diff against the original comes out empty. The explanation is Claude's reading, so review it as you would a pull request. Where the code does not say why, the document lists an open question.

  4. Work in it

    Edit the document. Teammates and agents can keep editing the code the usual way. Absorb and sync carry changes across, so the document stays true.

A prompt that works

Use the brashtag-literate skill. Turn invoice.py into invoice.lit. Keep every line of code exactly as it is, explain what each part does and why, and list anything you could not tell from the code as an open question. Do not change behaviour.

Brashtag: a tree in plain text

There are three kinds of node. A blob holds text. A bag holds blobs, codes and other bags, and can be tagged. A code holds text too, but is shielded: anything between its ticks is taken literally. Edit the text below and watch the tree it makes.

blob

Plain text. Any text except #, {, } and the tick character.

bag

A hash, a tag, braces, and whatever is inside: #card{ ... }. Bags nest.

code

Text between runs of ticks, for anything that would otherwise be read as notation. Use more ticks than the longest run inside. Three is usually enough, but one or two or ten are all valid.

any text
the tree

The parser is the one in the brashtag repository; this page runs its JavaScript build. Programs written on it include a Markdown-like converter to HTML, a flashcard program and a tree-to-Graphviz tool. The repository also has an Emacs mode.

Seven conventions for programs

Brashtag only says what a tree looks like. These conventions are what the literate tools do with it. Press a button to load an example into the editor above.

Four characters to keep out of blobs and tags

  • A #, {, } or tick in running text is read as notation. Put it in a code node.
  • Tangle reads the whole file as one document, so a stray brace on line 3 can hide an error on line 300. The message names the line it noticed.

Big programs: chapters

A literate program can be spread over many files. #include{pricing.lit} in one file is replaced by the text of that file, so a large codebase can have a chapter for each module or subsystem, and the root file reads as the introduction. The tools are given the root and see one document: chunk names stay global, so one chapter can use a chunk written in another.

[[code:shop/shop.lit:shop.lit (the root)]] [[code:shop/pricing.lit:pricing.lit]] [[code:shop/report.lit:report.lit]]

Here is that project through the tools. Every message and every address names the chapter file and the line in it, and absorb writes only the chapter that changed. It does not touch the prose, which still says 12: after absorbing, the author reads the diff and fixes the sentence.

[[term:t8:lit tangle shop.lit .]] [[term:t8:lit addr shop.lit shop.py:3]] [[term:t8:lit addr shop.lit report.lit:8]] [[term:t8:lit absorb shop.lit]]

Rules for chapters

  • Each chapter must be balanced on its own: every #tag{ is closed in the same file.
  • A file may be included once, and cycles are refused. A missing file is an error naming the file and the line of the directive.
  • In the woven page the first h1 is the title and later ones are chapters. Weave and lint treat the whole as one document.
  • The live editors on this page read a single text, so they do not follow includes. The run above is real output of the lit binary.

What happened

    Tangle rewrites the file from the document and keeps a copy of any edit it replaces. Absorb folds file edits into the document, and refuses if the document changed too. Merge compares both sides with what they were at the last sync, brings every separate change across in both directions, and asks you about the rest.

    Leave gaps for an assistant

    Sometimes you know what a chunk must do and have not written it. Say so in the document: put a bag inside the chunk, #agent-fill-in{what the code must do}. Tangle ignores it, so the program still builds around the gap. lit fill then does what you would do before writing the code: it reads the section's prose, the headings above it, the chunks that use this one up to the files, the chunks it uses, the other gaps, and the generated file around the hole. It sends that to an assistant, checks what comes back, and writes it into the document.

    The document, with two gaps

    [[code:words.lit:words.lit]]

    What the assistant is given

    Each gap becomes a prompt of ten sections, general first and specific last. When the document is large, the distant ones are trimmed first and the task and the chunk never are. Look at one without calling anybody:

    [[term:t9:lit fill words.lit --list]] [[term:t9:lit fill words.lit --dry-run --show-context]]

    The assistant is anything that reads a prompt on standard input and prints a reply, or the Anthropic API when ANTHROPIC_API_KEY is set. In the run below it is a canned shell script, so that the example is reproducible; a model takes its place with --agent anthropic or --agent 'claude -p'. Each answer is checked before it is written: the whole program must still parse and tangle, generated Go and JSON files must be valid, and a reply with TODO in it is not an answer. A check of your own, such as go vet, runs on the tangled program in a scratch directory once the last gap is filled, and a failure goes back to the assistant with its error.

    [[term:t9:lit fill words.lit --agent 'sh agent.sh' --check 'go vet main.go']]

    The code is in the document now, with your words kept as prose above it, and every fill is recorded beside it. Review is for the person who comes back later. It checks again, optionally asks a second assistant, and lets you approve each fill, or reject it, which puts your original gap back.

    [[term:t9:lit review words.lit --ai --agent 'sh review.sh']] [[term:t9:lit review words.lit --approve-all]] [[term:t9:lit tangle words.lit .]] [[term:t9:go run main.go < sample.txt]]

    What this does and does not do

    • The assistant writes code for a gap. It never edits your prose, and it never touches code outside the gap.
    • A fill is not trusted because it passed checks. lit review exists so that a person looks at each one, and the second opinion is a model, which can be wrong.
    • The scripts in this demo are fakes. Against a real model the code, and the number of retries, will differ.

    The toolbelt

    Each tool is a subcommand of one Go binary, lit, built from the standard library and the brashtag parser and nothing else. The skill that teaches an assistant the notation is inside the binary too, and it carries the same tools a second time as Python scripts that need only Python's standard library, so an assistant with just the skill folder can write literate programs and run every tool, including fill and review, with python3.

    [[svg:../internal/skill/files/docs/tools.svg|How the tools move text between the document, the generated files and the woven page.]]

    It tangles itself

    The tools are themselves a literate program, split into thirty-one files: a root and a chapter for each tool or subsystem, ordered by importance, with the plain details in an appendix at the end. Tangling it writes every Go source, the skill's files, the tests, the build script and this page: the page you are reading is one of the chapters. The build vets and tests the Go program, then tangles the document a second time with the binary it just built. The two outputs must be identical. Last, the build runs the tests of the Python scripts and checks that they tangle the document to the same files as the binary.

    __CODE__lines of code
    __PROSE__words of prose
